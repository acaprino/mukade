# Local MCP Chat Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans task by task. The user authorized complete implementation, tests and documentation without intermediate approval pauses.

**Goal** — Deliver the shared local MCP chat service, CLI, harness setup and reproducible verification.

**Architecture** — Extend the existing SQLite bus with durable member identities, events and delivery receipts. A single background Rust process owns it and exposes the official MCP SDK transport. CLI operations use that endpoint.

**Tech stack** — Rust 2024, existing rusqlite/serde/uuid/chrono, official rmcp 2.2.0, Tokio, Axum, reqwest and toml_edit. Pin cached compatible versions in Cargo.lock. MCP 2025-11-25 is the initial advertised revision. Enable 2026-07-28 only after SDK and interoperability tests prove it.

**Spec** — [Local MCP chat design](../specs/2026-11-11-mcp-chat-design.md).

## Global constraints

- One service per canonical data directory, protected credentials, loopback only.
- `mukade chat start/status/stop` control the process. Domain CLI operations use the running service.
- Preserve existing library and session interchange behavior and existing persisted schema data.
- Require exact native IDs and allow observation revocation in closed rooms.
- Mutation request IDs and delivery batch IDs survive restart. Ack commits only its staged delta.
- Message limit 65,536 UTF-8 bytes. Blocked reason limit 200 Unicode scalars. Default page budget 8,000 scalars, default wait 30 seconds, maximum 300 seconds.
- Full permitted text is masked before truncation and fingerprinting. Native observation text is never stored in SQLite.
- Existing 1 GiB free-space policy permits receipt and cleanup writes below that floor.
- HTTP body limit 1 MiB, query page default 100 / maximum 500 items, concurrent waits maximum 64, observation memory cache 16 MiB, export/query snapshot lifetime 10 minutes. Requests exceeding limits receive explicit errors.
- User authorized current-checkout continuation. Git branch creation failed because `.git` is read-only. Commit attempts cannot gate implementation.

## Review focus

- Retry after commit and room closure must replay the committed result, including leave with its revoked handle.
- Multiple workers sharing an instruction need independent completion states.
- Observation source edits and rebinds must never let stale acknowledgements consume new text.
- A stale stop and two simultaneous starts must not affect another service instance.
- Configuration editing must preserve unrelated user settings, including comments where the format supports them.

## Interfaces and schemas

The domain entry point is `Bus::chat_call(&mut self, operation: &str, arguments: serde_json::Value, roots: &StoreRoots) -> Result<serde_json::Value, ChatError>`.
`ChatError` exposes `code`, `message`, `retryable` and `exit_code()`. It never includes raw credential values.
`chat_tool_definitions() -> Vec<serde_json::Value>` returns complete tool name/description/inputSchema/outputSchema/annotations, independently of rmcp types.
Serde argument structures reject unknown fields. All mutation schemas require UUID `request_id`. Room names are accepted only by open, with immutable `room_id` everywhere else.

| Operations | Arguments beyond request_id for mutations |
|---|---|
| open | name |
| close/reopen | room_id |
| delete | room_id, expected_revision, confirm=true |
| rooms | cursor?, limit? |
| join | room_id, harness, role, name?, session_id? |
| rejoin | room_id, member_id, session_id? |
| leave/unbind | room_id, member_handle |
| members | room_id, cursor?, limit? |
| candidates | harness, cwd?, cursor?, limit? |
| bind | room_id, member_handle, harness, session_id, source_ref? |
| send | room_id, member_handle, text, recipients? |
| signal | room_id, member_handle, instruction_event_id, signal, reason? |
| read | room_id, member_handle, budget_chars?, ack_batch_id? |
| peek | room_id, member_handle, budget_chars? |
| wait | room_id, member_handle, budget_chars?, ack_batch_id?, addressed_only?, timeout_seconds? |
| ack | room_id, member_handle, batch_id |
| observe | room_id, member_handle, target_member_id, budget_chars?, ack_batch_id?, latest?, last_turns? |
| ledger | room_id, member_handle?, actor?, kind?, since?, until?, mention?, text?, cursor?, limit? |
| export | room_id, member_handle?, cursor?, limit? |

Schemas may refine query shape if the final documentation and all callers are updated together. Every result has stable IDs and machine-readable status. Domain errors become MCP `isError` results. `wait` staging is synchronous and returns waiting status when no trigger exists. The async service releases database locks, registers/rechecks notification state, and calls again until result/deadline/cancellation. Snapshot read work holds no write transaction.
