## Run 2: two agents talk

Script: [`chat-live/two-agents.sh`](chat-live/two-agents.sh) `<mukade executable>`.

| step | who | tool calls | result |
|---|---|---|---|
| 1 | Codex | `chat_join`, then `chat_wait` (addressed only, 240 s) | joined as `codex-1`, blocked waiting |
| 2 | Claude Code | `chat_join`, `chat_members`, `chat_send` | joined as `claude-1`, sent `@codex-1 What is the capital of Italy? Answer in one word.` |
| 3 | Codex | the wait returns; `chat_ack`, `chat_send` | received the question, acknowledged it, sent `@claude-1 Rome` |
| 4 | Claude Code | `chat_wait`, `chat_ack` | final line: `codex-1 replied: "@claude-1 Rome"` |

Room ledger afterwards: `open`, `join codex-1`, `join claude-1`, `message` from `claude-1`,
`message` from `codex-1`. Both members still in the room.

Findings:

- **Codex behind a TLS proxy.** The launching environment routes HTTPS through a local proxy
  (`HTTPS_PROXY`, CA in `NODE_EXTRA_CA_CERTS`) that Codex does not trust: the first attempt ended
  in `workspace routing discovery failed` before any model call. Run without those two
  variables, as `docs/verification/source-model-summary-live.md` already records. Codex's MCP
  connection to the loopback endpoint was not the problem.
- **A harness asked to talk to a member that is not there does not guess.** In the failed
  attempt Claude Code found no Codex member and stopped without sending, saying so.
- **The user's own Codex `Stop` hook reported `Stop Failed`** at the end of the turn. It is not
  part of mukade and did not affect the exchange.

## Run 5: launched instances that listen

Script: [`chat-live/launch-listen.sh`](chat-live/launch-listen.sh) `<mukade executable>`. Both
instances are `claude -p --model haiku` started by `mukade chat launch claude_code --room live
--listen 150 --max-wakes 1`; neither prompt mentions waiting or reading.

| step | what happened |
|---|---|
| 1 | A (`claude-1`) starts; its SessionStart hook joins it and gives the model its name, handle and rules |
| 2 | B (`claude-2`) starts, is told by the hook what is in the room, and sends `@claude-1 What is 6 times 7?`; then it ends its turn and its Stop hook listens |
| 3 | A greets the room and ends its turn; its Stop hook finds the question addressed to it and restarts it |
| 4 | A sends `@claude-2 6 times 7 is 42.`; B's Stop hook wakes on it |
| 5 | B's final line: `claude-1 replied: 6 times 7 is 42.` |

The first two attempts failed, and the failures are what the adapter's last fixes are about:

- **Its own messages came back to a member** and counted as news: A woke on its own greeting and
  spent its only wake-up before the question came. A member's own events are no longer handed
  back (`a_member_is_not_handed_its_own_messages`).
- **A join, or a message to the whole room, woke a listening instance.** B woke on A's greeting,
  not addressed to it, and stopped before the answer. Listening now restarts an instance only for
  a message or signal addressed to it; the others stay unread and come with it
  (`a_join_alone_does_not_wake_a_listening_instance`,
  `a_message_to_the_room_does_not_wake_a_listening_instance`).

## Run 6: a launched Codex, on a bench

Script: [`chat-live/codex-bench.sh`](chat-live/codex-bench.sh) `<mukade executable>`, with
[`chat-live/mock_responses.py`](chat-live/mock_responses.py), a local stand-in for the Responses
API. The bench's `CODEX_HOME` is a scratch folder with no plugins and the mock as its model
provider: no model is paid for, the user's Codex configuration is neither read nor written. Codex
CLI 0.167.2.

`mukade chat launch codex --room bench --listen 30 --max-wakes 1 -- exec --ephemeral … "Say hello."`:

| check | result |
|---|---|
| hooks | `SessionStart Completed`, `UserPromptSubmit Completed`, `Stop Blocked` (Codex goes on), `Stop Completed` (no wake-up left) |
| first request to the model | a developer message `[mukade chat] You are codex-1, a peer in a local chat room …` |
| MCP | the request offers a namespace `mcp__mukade` with the 21 chat tools: the server answered with the credential Codex read from the environment (`env_http_headers`) |
| second request | a user message `<hook_prompt hook_run_id="stop:2:…<session-flags>…">[mukade chat] New in your room, for codex-1 …`: the tester's `@codex-1 are you there?` |
| room | members `codex-1`, `tester-1` |

What the probes before it showed, against the installed Codex:

- **Hooks given with `-c` are skipped, silently, until trusted.** Only the user's own trusted
  hooks ran (three at session start, two at prompt, one at stop, as `[hooks.state]` in
  `~/.codex/config.toml` lists). They come from the source `<session-flags>`.
- **Codex on Windows runs a hook with PowerShell.** `"C:/…/mukade.exe" chat hook …` is a
  PowerShell syntax error and fails without output; `& 'C:/…/mukade.exe' chat hook …` runs. The
  read-only sandbox does not confine hooks: they reached the loopback service and wrote mukade's
  state.
- **`--dangerously-bypass-hook-trust` runs every untrusted hook, not only mukade's.** One probe
  used it against the installed Codex and ran the user's installed but never trusted plugin
  hooks too, in a scratch folder (32 of 33 failed there). mukade never passes the flag; the
  bench uses it only where no other hook exists.

Not established **[U]**: that trusting the hooks once with `/hooks` holds across launches (the
hook definitions are the same for every launch so that it should). A real model in a launched
Codex: run 7.

## Run 8: Codex trusted once, launched with its plugins and no bypass

1. `mukade chat trust codex --dry-run`: Codex's `app-server` lists mukade's three hooks as
   session flags, all `untrusted`. Nothing written.
2. `mukade chat trust codex`: three `hooks.state` entries added to `~/.codex/config.toml`
   (`C:\<session-flags>\config.toml:session_start:0:0`, `…:user_prompt_submit:0:0`,
   `…:stop:0:0`, each with the hash Codex listed). Diff against a copy taken before: those
   three entries only; the user's other entries and comments unchanged. All three now `trusted`.
3. [`chat-live/codex-claude-launch.sh`](chat-live/codex-claude-launch.sh) without
   `features.plugins=false` and without `--dangerously-bypass-hook-trust`: Codex starts with its
   plugins. Same steps and answer as run 7 (`@claude-1 Jupiter is the largest planet in the solar
   system.`); mukade's hooks `Completed` / `Stop Blocked`. The other `Failed` hook lines are the
   user's own trusted plugin hooks, unrelated to mukade.

Trust given once holds across launches: the hook commands are the same for every launch (the
Stop timeout is fixed), so their hash is too. Unit tests over a fake Codex server:
`harnesses::codex::trust_tests` (only mukade's session-flag hooks are written, with the hash Codex
listed; dry run writes nothing; trusted ones are not rewritten; a missing hook writes nothing; a
refused hash reports `not_trusted`).

## Run 9: the OpenCode and Pi launch kits, on Linux, without the harnesses

Not a live run: no OpenCode or Pi process ran (this machine may not execute the downloaded
packages). The kits were written against the plugin APIs of the installed packages, read from
their own files: `@opencode/plugin` 2.2.7 (`session.hook("prompt" | "experimental.idle")`,
`session.synthetic`, `session.get`; a configured plugin is a folder, its `server` entry the module
whose default export is `{id, setup}`, read from the `@opencode/cli` 2.2.7 binary) and
`@earendil-works/pi-coding-agent` 1.5.2 (`docs/extensions.md`: `session_start`, `input`,
`before_agent_start`, `agent_before_settle`, `registerMcpServer`; `docs/mcp.md`: `exposure`).

`tests/chat_plugin_kits.rs` writes each kit with `chat_launch`, then Node plays the harness around
it (`tests/support/plugin_kit_driver.mjs`) against a real `mukade chat start` service and a second
member that writes to the room. The kit's hooks run the real `mukade chat hook`. Seen for both:

1. the first hook joins and introduces the member (`pi-1`, `opencode-1`);
2. a message written to the room comes with the next prompt (Pi: the returned `message`;
   OpenCode: a synthetic message with `resume: false`, ahead of the prompt; when the session
   refuses it, the text goes ahead of what was typed);
3. listening: a message addressed to the member, sent a second later, makes the run go on
   (Pi: a `custom_message` entry with `continue: true`; OpenCode: a synthetic message that resumes);
4. a prompt typed while listening ends the wait (Pi: the `input` event; OpenCode: the next
   `prompt` hook), and so does Escape in Pi (the run's `signal`);
5. OpenCode: a subagent's child session (`parentID` set) is not a member; an idle session whose own
   background work is running does not wait.

Found by this run: a stopped listener's last `wait` went on in the service, holding the member's
stream, so the next prompt's hook failed with `stream_busy` and its news waited for a later one
(the same happened after a Claude Code Stop hook was interrupted). The hook now closes its client
on SIGTERM and the client cancels its call in flight (`notifications/cancelled`), so the service
ends the wait: the next prompt's hook answered in 110 ms, against 4.8 s with the slice alone.
Listening waits in slices of 5 s, and a hook that meets `stream_busy` waits up to 8 s for the
stream: on Windows, where a stopped hook gets no signal, that bounds the delay.

## Run 10: a launched OpenCode, Pi and Claude Code, real models, on Windows

Script: [`chat-live/opencode-pi-claude-launch.sh`](chat-live/opencode-pi-claude-launch.sh)
`<mukade executable>`. Windows 11, debug build of `ed0130d`; OpenCode 2.2.5 (model
`openrouter/~anthropic/claude-haiku-latest`), Pi 1.4.0 (its default model), Claude Code 2.1.322
(`haiku`). The kits were written against OpenCode 2.2.7 and Pi 1.5.2 (run 9); both older releases
have every hook and call they use. OpenCode wrote into a scratch `OPENCODE_DB`; no configuration of
any harness was written.

Each of the three is started with `mukade chat launch <harness> --room r --listen 120`; OpenCode and
Pi greet the room and end their turn, Claude Code then asks each one question. Attempt 3, with
`PI_ARGS="-ne -e builtin:mcp"`:

| step | what happened |
|---|---|
| 1 | Pi (`pi-1`) and OpenCode (`opencode-1`) join and greet the room with `chat_send` |
| 2 | Claude Code (`claude-1`) joins, sends `@opencode-1 Which planet is the largest in the solar system?` and `@pi-1 What is the capital of France?` |
| 3 | both listening instances wake on the message addressed to them and answer: `@claude-1 Jupiter. It is the largest planet…`, `@claude-1 Paris` |
| 4 | Claude Code's Stop hook wakes on each answer; its final lines name both members and both answers |

What run 9 could not settle, now seen:

- **OpenCode loads the plugin folder from `OPENCODE_CONFIG_CONTENT` with `--standalone`:** the
  plugin's hooks ran in the private server (join, synthetic messages); the user's own background
  OpenCode service was not used.
- **`{env:…}` is expanded in the MCP entry:** the model's `mukade_chat_send` calls reached the
  service, which refuses a call without the bearer token and service id the two headers carry. The
  tools are direct (`codemode: false`): `mukade_chat_send`, not a Code Mode script.
- **The synthetic message comes ahead of the prompt.** `opencode session export`, in order:
  `synthetic` (`metadata.source: mukade-chat`, `[mukade chat] You are opencode-1, a peer…`), the
  typed `user` prompt, the assistant's `mukade_chat_send`; after the turn, a second `synthetic`
  (`New in your room, for opencode-1 … #7 claude-1 …`) that resumed the session, the answer, `idle`.
- **Pi loads the `.ts` extension and connects the server it registers** while the extension loads,
  with Pi's own MCP (`builtin:mcp`).

Found on the way:

- **Attempt 1:** the script put the scratch `OPENCODE_DB` in the work folder, which also held
  `MUKADE_DATA_DIR`; the OpenCode launch was refused (`Chat data directory is inside a native
  harness store`), as the service's guard says it should. Claude Code then found no OpenCode member
  and said so instead of sending. The script now gives OpenCode a folder of its own.
- **Attempt 2, Pi through an MCP package:** the author's Pi settings turn the built-in MCP off
  (`"extensions": ["-builtin:mcp"]`) and load `pi-mcp-adapter` 5.3.1, which takes
  `registerMcpServer` and ignores `exposure: direct` (`ignored settings exposure: direct`). Pi still
  joined, greeted and answered: the same exchange as attempt 3 passed with the package.
- **OpenCode's own Code Mode catalog** (the user's other MCP servers) adds a system message after
  the first turn; the model spent one short turn on it. Not mukade's.

## Found and fixed during these runs

`mukade chat start` on a disk with less than 1 GiB free failed with `Chat service failed before
readiness`, without the reason. The free-space floor was right (a new database is not made below
it); the message was not. Now the child reports its own error to the parent, and a low-space
refusal says which folder and to free space or set `MUKADE_DATA_DIR` elsewhere
(`tests/chat_cli.rs` `a_service_that_fails_to_start_reports_its_own_reason`,
`bus::store` `a_low_space_refusal_keeps_its_reason_as_a_chat_error`).

Also found while scripting these runs:

- **Capturing `mukade chat start` hung on Windows.** The background service inherited the
  caller's output pipe, so `x=$(mukade chat start)` waited until the service stopped. The service
  is now spawned without the caller's standard handles
  (`start_can_be_captured_and_after_stop_the_folder_can_be_removed`).
- **`chat stop` answered before the service's process had exited**, so removing the data folder
  right after it could find the database still open. It now waits for that process too.
- **`--listen 1` did not wait at all**: the time left was rounded down to whole seconds. It is
  rounded up (`listening_ends_after_its_time_and_after_its_wake_ups`).
